## 一、必做项目深度分析

### 1. paper-qa（Future-House / PaperQA2）

**项目定位与规模**【已核验 + 第三方数据】
- 仓库：https://github.com/Future-House/paper-qa （查询日期 2026-10-08）
- Star：约 **9.2k**（repositorystats.com 2026-09-24 快照 9,241；star-history 2026-08-01 约 9k）【第三方数据，非 GitHub 页面直读】
- 语言：Python；许可证 Apache-2.0
- 架构形态：**纯 Python 库**（`pip install paper-qa`）+ CLI（`pqa ask`），**无内置 Web 前端**；定位是"高精度科学文献 RAG 库"，可被二次开发调用
- 配套论文：arXiv:2312.07559（PaperQA）、arXiv:2409.13740（PaperQA2 / "Language agents achieve superhuman synthesis of scientific knowledge"）、arXiv:2412.21154（Aviary）

**技术架构**

| 维度 | 设计 | 核验状态 |
|---|---|---|
| 检索策略 | 默认 OpenAI `text-embedding-3-small` 稠密向量；向量库默认 **Numpy 内存向量库**（in-memory，无 ANN 索引，因为 chunk 数 < 1k），可切 Qdrant；**原生支持 hybrid 检索**：`embedding="hybrid-text-embedding-3-small"` 即 dense + sparse keyword（基于 token modulo 的稀疏向量），或 `"sparse"` 纯稀疏 | 【已核验】README "Embedding Model" 节 |
| Rerank | **不是 cross-encoder reranker**，而是 **LLM-based re-ranking + contextual summary（RCS）**：先向量检索 top-k chunk，对每个 chunk 用 LLM 结合当前 query 生成"上下文相关摘要"（contextual summary），再让 LLM 从这些摘要里挑选最相关的 N 条喂给最终答案 | 【已核验】README "PaperQA2 Algorithm" 三阶段表 + Settings Cheatsheet |
| Agent 编排 | v5 默认 `ToolSelector` agent（agent_llm 驱动），工具包括 `SearchPapers`（LLM 生成关键词 → 检索本地索引 → 新 PDF 入 state）、`GatherEvidence`（向量检索 + LLM 重排 + 摘要）、`GenerateAnswer`；agent 可任意顺序调用工具（窄搜/宽搜/多次 gather）。也支持 `"fake"` agent：硬编码 search→gather→answer 路径，省 token | 【已核验】README "Agentic Adding/Querying Documents" |
| **引用溯源（最关键）** | **生成式引用 + key 映射**：每个 chunk 在入库时分配一个 citation key（形如 `pqac-abcd1234`），QA prompt 明确告诉 LLM "You can cite the context using the key like (pqac-abcd1234)"；LLM 在生成答案时直接插入这些 key；系统在生成后把答案里出现的 key 映射回原始 chunk / 论文元数据，最终输出 `formatted_answer` + `context`（每条证据对应来源）。论文元数据通过 Crossref / Semantic Scholar / Unpaywall 多源合并，自动生成 BibTeX 风格引用 | 【已核验】README "Customizing Prompts" 节原文 + "Using Clients Directly" 节 |
| 分块 / PDF 解析 | 支持 PDF/txt/md/html/docx/xlsx/pptx/代码；PDF 解析后端可选 Docling、Nvidia nemotron-parse；**图片/表格处理有亮点**：`ParsedMedia` 对象与 chunk 一对多关联，并用 `parsing.enrichment_llm` 给每张图/表生成 synthetic caption（合成描述），caption 参与 embedding 偏移但不污染上下文摘要原文 | 【已核验】README "Multimodal Support" |
| 缓存策略 | ① embedding 缓存：pickle 整个 `Docs` 对象即可复用 embedding；② index 复用：基于 Settings 对象 hash 建索引，下次同目录查询跳过已索引文件；③ 支持 `PQA_HOME` 环境变量统一管理索引目录 | 【已核验】README "Caching Embeddings" / "Reusing Index" |
| LLM 接入 | 通过 **LiteLLM** 统一接入（gpt-4o 默认、Claude、Gemini、Ollama、llama.cpp 均可），天然支持 OpenAI 兼容协议 → **DeepSeek API 可直接通过 LiteLLM 接入** | 【已核验】README "Choosing Model" |

**对用户技术栈的直接借鉴点**
1. **【直接照搬】引用 key 机制**：用户做的 `[n]` 编号引用，paper-qa 的做法是"每个 chunk 入库时分配唯一 key → prompt 里教 LLM 插 key → 生成后正则提取 key → 映射回原文"。这是最稳的"生成式引用"实现，比用户当前可能的"答案后处理映射"更简单可靠。**建议用户直接抄这个思路**：chunk_id = `pqac-<hash>`，prompt 里写死引用格式，生成后用正则 `\((pqac-[a-z0-9]+)\)` 提取再映射成 `[1] [2]`。
2. **【直接照搬】embedding 缓存 + index 复用**：pickle Docs 对象 / 基于 Settings hash 建索引，避免每次重启重 embed。用户用 Chroma 可以直接在 collection 里按文件 hash 去重。
3. **【需要改造】LLM rerank + contextual summary**：paper-qa 不用 cross-encoder，而是让 LLM 给每个候选 chunk 写"结合 query 的摘要"再挑。这招对**小 chunk 数（<30）**效果极好且省显存（不需要再跑一个 bge-reranker）。但用户已经打算做 rerank，建议二选一：要么学 paper-qa 用 DeepSeek 做 LLM rerank（省一个模型），要么用 bge-reranker（更快更便宜）。**论文消融显示 rerank 去掉后正确性掉 5-20 分，不能省**。
4. **【需要改造】OpenAI 依赖 → DeepSeek**：paper-qa 用 LiteLLM，DeepSeek 是 LiteLLM 一等公民，配置 `llm="deepseek/deepseek-chat"` 即可，几乎零改造。

**可借鉴点（1-3 条）**
- ① 引用 key 机制（chunk 级 citation key + 正则提取映射）—— **强烈建议抄**
- ② LLM-based contextual summary rerank（替代 cross-encoder 的轻量方案）
- ③ 多源论文元数据合并（Crossref + Semantic Scholar）—— 若用户项目要做"引用格式化输出"可参考

**可借鉴程度评分：高**
> 理由：paper-qa 是"带引用的学术 RAG"最直接对标，其引用机制、三阶段 pipeline（search→gather evidence→answer）、hybrid sparse+dense、LiteLLM 多模型接入几乎可以逐模块对照用户当前栈改造。缺点：默认 Numpy 向量库对个人项目够用但不是 Chroma；Web 前端要自己写。

### 2. OpenScholar（AI2 / Akari Asai 等）

**项目定位与规模**【已核验】
- 仓库：https://github.com/AkariAsai/OpenScholar （查询日期 2026-10-08）
- 配套论文：arXiv:2411.14199（"OpenScholar: Synthesizing Scientific Literature with Retrieval-augmented LMs"，已发表于 Nature 2026）
- 语言：Python；架构形态：**研究原型 / CLI 脚本**（`python run.py ...`），非产品化，无 Web 前端；配套发布了 retriever / reranker / 8B generator 的 HF checkpoint
- 数据规模：OSDS datastore = 4500 万篇开放论文、2.37 亿 passage embeddings【论文原文】

**技术架构**

| 维度 | 设计 | 核验状态 |
|---|---|---|
| 检索策略 | **三路召回**：① peS2o datastore 内 bi-encoder 向量检索 top-100；② LLM 从 query 生成关键词 → Semantic Scholar Search API 按被引数取 top-10；③ You.com web search API 取 top-10（限 arXiv/PubMed）。bi-encoder = Contriever 在 peS2o 上继续预训练（110M 参数） | 【已核验】论文 §2.1 |
| Rerank | **cross-encoder reranker**：基于 `BAAI/bge-reranker-large` 用 Llama-3-70B 生成的合成相关性标注微调（340M 参数）。附加 meta-filter：① 单篇论文最多 3 个 passage 进上下文；② 归一化 citation count 融入 rerank 分 | 【已核验】论文 §2.1 + README "Run OpenScholar inference" 的 `--ranking_ce --reranker OpenScholar/OpenScholar_Reranker --max_per_paper 3 --norm_cite` |
| 分块策略 | 每篇论文正文按**空白符切 250-word block**，每块前面拼接论文标题作为 passage | 【已核验】论文 §2.1 |
| **Agent / 推理编排（最关键）** | **自反馈迭代生成（self-feedback loop）**：<br>① 给 top-N passage + query → LLM 生成初始答案 y0（带 [n] 引用）<br>② 同一 LLM 对 y0 生成最多 3 条自然语言 feedback（"缺 X 任务的结果"、"组织混乱"等）<br>③ 若 feedback 指出缺信息，LLM 自动生成检索 query qk → 走 §2.1 检索 pipeline 补召回 → 并入 y_{k-1} 生成 y_k<br>④ 迭代直到所有 feedback 处理完 | 【已核验】论文 §2.2 + README flags `--feedback --posthoc --ss_retriever` |
| **引用溯源（最关键）** | **生成式 [n] 编号引用 + posthoc attribution 校验**：LLM 在生成 y0 时直接给句子打 [n]，n 对应传入的 passage 编号；最后一步由 LLM 做 **citation verification**：检查所有"需要引用的陈述"是否都有引用支撑，缺引用则**事后补插**（post hoc insertion），但不删句子。论文还提出 Cite-p / Cite-r / Cite-F1 指标，用 `osunlp/attrscore-flan-t5-xl`（FLAN-T5-XL）自动判定"claim 是否被 reference 支持" | 【已核验】论文 §2.2 "Citation verification" + 附录 B.3.3 |
| 缓存策略 | 离线预计算 passage embeddings（Google Drive 发布检索结果）；推理时直接加载预计算 ctxs | 【已核验】README "We released our retrieval results at google drive" |
| LLM 接入 | 支持开源 `OpenScholar/Llama-3.1_OpenScholar-8B`（vllm 推理），也支持 `--api openai` 接 GPT-4o | 【已核验】README |

**对用户技术栈的直接借鉴点**
1. **【直接照搬】posthoc citation verification**：用户做 `[n]` 引用最头疼的就是 LLM 瞎编引用号。OpenScholar 的解法是**生成后让 LLM 再过一遍**："检查答案里每个需要引用的论断是否都挂了 [n]，缺了就补"。这一步只要在 prompt 里加一段，DeepSeek 完全能做，**强烈建议加**。
2. **【直接照搬】`max_per_paper` 去重**：单篇论文最多取 3 个 passage，避免一篇论文霸屏上下文。用户 RRF 融合后加这一行 dedup 即可，成本为零。
3. **【可选借鉴】自反馈 loop**：y0 → feedback → 补检索 → y1。这个对求职项目是**加分项**（面试可讲"我做了 iterative refinement"），但实现成本是多 1-2 次 LLM 调用。建议作为 M2/M3 阶段的扩展，不是 M1 必须。
4. **【不建议照搬】bi-encoder/cross-encoder 自研微调**：用户用 bge-m3 + bge-reranker 开箱即用即可，不需要在 peS2o 上继续预训练。
5. **【需要改造】三路召回**：OpenScholar 的 Semantic Scholar API + You.com web search 对个人项目过重，用户做的是"本地 PDF 库问答"，不需要 web search。但 **LLM 从 query 生成关键词再检索 S2** 这个思路，对用户的"中英术语词典查询改写"是一个升级方向。

**可借鉴点（1-3 条）**
- ① **posthoc citation attribution**（生成后校验引用完整性）—— **强烈建议抄**
- ② `max_per_paper` 单篇去重 + 归一化 citation 权重融合 rerank
- ③ 自反馈迭代生成 pipeline（y0 → feedback → 补召回 → y1），可作为面试亮点

**可借鉴程度评分：高**
> 理由：OpenScholar 是"学术 RAG 引用准确性"的 SOTA 论文，其 posthoc citation verification、self-feedback loop、250-word + 标题拼接分块、cross-encoder rerank 都是经过消融验证有效的模块。缺点是它是研究原型，代码工程化程度低，且依赖 4500 万篇论文的 datastore（用户用不上），需要把"pipeline 思想"抽取出来套到自己的 Chroma + bge-m3 上。

### 3. GPT-Academic（binary-husky）

**项目定位与规模**【已核验】
- 仓库：https://github.com/binary-husky/gpt_academic
- Star：**71.4k**（GitHub 页面直读，查询日期 2026-10-08）；Fork 8.3k
- 语言：Python；许可证 GPL-3.0
- 架构形态：**Gradio Web 应用** + 插件系统（`crazy_functions/` 目录热加载）；定位是"LLM 学术工作台"，不是 RAG 问答系统

**技术架构**
- 检索策略：**无 RAG、无向量库、无 BM25**。PDF 论文全文翻译/总结是**直接把 PDF 提取文本切块后多线程喂给 LLM**（README 自述"如果每个部分超过了长度，则截断（目前这个方案太粗暴了）"）【已核验】
- Agent 编排：**函数插件制**（不是 ReAct agent），每个按钮 = 一个前缀 Prompt + 调用 LLM；有"虚空终端"插件用自然语言调度其他插件；v3.60 引入 AutoGen 作为新插件基石
- 引用溯源：**无**。它输出的是润色/翻译/总结文本，不做引用编号
- 分块：PDF 用 PyMuPDF 提取后按章节/长度切，无结构化解析
- 缓存：对话可保存为 HTML 再加载，无 embedding/LLM 响应缓存
- LLM 接入：request_llms/ 目录手写 bridge，支持 OpenAI/ChatGLM/Qwen/DeepSeekCoder/文心一言等十几种

**对用户技术栈的直接借鉴点**
- 几乎没有架构层面可抄的（它根本不是 RAG）。
- **可借鉴的是产品形态**：用户后续做 M3 写作助手（大纲/润色/综述）时，GPT-Academic 的"快捷按钮 = 前缀 Prompt"插件制是最省心的 UI 设计——每个功能一个按钮，前端不用写复杂交互。

**可借鉴点（1-3 条）**
- ① "快捷按钮 = 前缀/后缀 Prompt"的插件式 UI（M3 写作助手阶段可参考）
- ② 多 LLM 负载均衡（多 API key 轮询）—— 若用户 DeepSeek 想搞多 key 容灾可参考
- 其余不值得借鉴

**可借鉴程度评分：低**
> 理由：它是"LLM 学术工作台"不是"论文问答 RAG"，检索/引用/分块这些核心模块都没有，对用户当前栈帮助有限。Star 高只是因为功能广（翻译/润色/代码解释/语音），不是因为 RAG 架构先进。

### 4. ChatPaper（kaixindelele）

**项目定位与规模**【已核验 README + 第三方 star】
- 仓库：https://github.com/kaixindelele/ChatPaper
- Star：约 **19.6k–20k**（openagentskill 2026-06 快照 19.6k；README 自述 2023.04 破 1 万星）【第三方数据】
- 语言：Python；架构形态：**命令行脚本**（chat_paper.py / chat_arxiv.py）+ 简易 Flask Web 服务
- 定位：arXiv 论文批量摘要工具，**不是交互式问答**

**技术架构**
- 检索策略：**无 RAG、无向量库**。用 `arxiv.py` 包按关键词爬 arXiv，下载 PDF
- 处理流程：按章节切分（abstract+introduction → method → conclusion），分三次喂 GPT-3.5 总结，超长截断【已核验 README "技术原理"】
- Agent 编排：无 Agent，固定 pipeline
- 引用溯源：**无**
- 分块：按章节标题正则切
- 缓存：离线预总结了 3w+ CCF-A 论文（README 提及）
- LLM 接入：OpenAI API（apikey.ini 配置）

**对用户技术栈的直接借鉴点**
- 几乎没有。它解决的是"批量速览 arXiv 新论文"，用户解决的是"对本地 PDF 库做带引用的问答"。
- 唯一可参考：其总结 prompt 模板（研究背景 / 过去方案 / 本文方法 / 实验效果 四段式）—— 如果用户 M3 阶段要做"单篇论文摘要"功能可直接抄。

**可借鉴点（1-3 条）**
- ① 四段式论文总结 prompt（背景→过去问题→方法→效果）
- 其余不值得借鉴

**可借鉴程度评分：低**
> 理由：无检索、无引用、无交互，是 2023 年的初代 ChatGPT 套壳脚本，对 RAG 架构没有参考价值。

## 二、可选 / 补充项目快速分析

### 5. RAGFlow（infiniflow）

- Star：约 **91.7k**（andrew.ooo 2026-10-05 核验 91,688；agentindex 2026-10-05 91.7k）【第三方数据，非 GitHub 页面直读】
- 语言：Python（后端）+ Web 前端；架构形态：**完整 RAG 引擎产品**（Docker 一键部署，带 Web UI）
- 检索策略：**hybrid retrieval（向量 + BM25）+ fused reranking（RRF 融合多路召回）**；v0.27 引入 Agentic Retrieval（agent 决定搜什么、要不要补搜）【已核验 deepwiki.com / infiniflow.org blog】
- Rerank：多阶段 rerank + 阈值过滤；底层用 Infinity 向量库，支持 dense + sparse + full-text + tensor reranker 三路融合
- 分块 / 解析：**DeepDoc 深度文档理解引擎**是其核心卖点——OCR（15+ 语言）+ 版面分析（10 类组件：正文/标题/图/图注/表/表注/页眉/页脚/参考文献/公式）+ 表格结构识别（TSR，处理跨列表头）；多模板 chunking（Naive/Book/Law/Paper/Presentation）【已核验 pyshine.com / ragflow.io blog】
- 引用：grounded citations，答案可点击追溯到 chunk【已核验 FAQ】
- 缓存：多 pass indexing（解析一次，多次索引）
- **对用户借鉴**：
  - ① **DeepDoc 的 PDF 解析思路**：用户做论文 PDF 一定会遇到双栏、表格、公式。RAGFlow 的版面分析 + 表格结构识别是开源里最成熟的方案，**可以考虑直接用其 DeepDoc 后端替代 PyMuPDF 粗糙切分**（`pip install ragflow` 或单独调 DeepDoc API）。
  - ② **RRF 多路融合**：用户已经自己实现 RRF，RAGFlow 的"dense + sparse + full-text 三路 RRF + rerank"是工业界验证过的配比，可参考其权重。
  - ③ Paper chunker 模板（按论文章节切）—— 比固定长度切分更适合论文。
- **可借鉴程度：中高**（工程化产品太重，不能直接抄，但 PDF 解析和 RRF 配比可借鉴）

### 6. QAnything（netease-youdao）

- 架构形态：**企业级本地知识库 QA 系统**（Docker + Triton + Milvus + Sanic 后端 + Web 前端）
- 检索策略：**两阶段检索**——第一阶段 BCEmbedding（bce-embedding-base_v1）稠密召回，第二阶段 bce-reranker-base_v1 重排；README 明确给出"MTEB 榜单上 bce-embedding + bce-reranker 是 SOTA 组合"【已核验 README】
- 引用：未强调引用编号机制
- LLM：基于 Qwen 微调
- **对用户借鉴**：
  - ① 两阶段检索（embedding 粗排 → reranker 精排）是标准范式，用户已经在做
  - ② BCEmbedding 是中英双语 SOTA，**但用户已经选了 bge-m3**（bge-m3 也是多语言 + 支持 dense/sparse/multi-vector），不需要换
  - ③ Milvus vs Chroma：QAnything 用 Milvus 是因为企业级数据量，个人项目 Chroma 足够
- **可借鉴程度：中**（架构思路标准，但模型选型用户已有更好的 bge-m3）

### 7. KAG（OpenSPG / 蚂蚁 + 浙大）

- 架构形态：**知识图谱增强生成框架**（KAG-Builder 建图 + KAG-Solver 逻辑推理 + KAG-Model）
- 核心：用 SPG（语义增强可编程图谱）把文档抽成三元组，检索时走 logical-form 引导的混合推理（图遍历 + 向量），解决多跳问题
- **对用户借鉴**：**低**。个人求职项目没必要建知识图谱——构建成本高（需要 LLM 抽三元组）、调试复杂、对"论文问答"这种短上下文问题收益不明显。面试时可以提一句"我知道 GraphRAG/KAG 适合多跳推理，但本地 PDF 库规模下向量+BM25 已够"。
- **可借鉴程度：低**

### 8. langchain-chatchat（chatchat-space）

- 架构形态：**中文本地知识库 QA 教程项目**（FastAPI + Streamlit WebUI）
- 检索策略：**单路向量检索 top-k**（默认 m3e-base embedding），FAISS/Milvus/PGVector 可选；**无 BM25、无 rerank、无混合检索**【已核验 README】
- 引用：无
- 分块：ChineseRecursiveTextSplitter（按中文标点递归切）
- **对用户借鉴**：低。它是 2023 年的入门教程，架构比用户当前栈还基础。唯一可参考：其 `ChineseRecursiveTextSplitter` 对中文论文切分比 RecursiveCharacterTextSplitter 友好。
- **可借鉴程度：低**

### 9. Onyx（原 Danswer）

- Star：约 20k–26k（pyshine 2026-04 报 26k；appliedai.tools 报 20k+）【第三方数据】
- 架构形态：**企业搜索 + AI 聊天平台**（MIT 协议，40+ 数据连接器）
- 检索策略：**hybrid search（vector + BM25）over OpenSearch** + cross-encoder rerank + contextual chunking + multi-pass indexing；支持 permission-aware retrieval；v2026 引入 StructRAG / Agent Search【已核验 onyx.app 官方博客】
- LLM：通过 LiteLLM 接 OpenAI/Anthropic/DeepSeek/Ollama/vLLM
- **对用户借鉴**：
  - ① contextual chunking（切分时带前后文）—— 用户切 PDF 时可参考
  - ② hybrid search over OpenSearch 的工程化——但用户用 Chroma + 自实现 BM25 + RRF 已经是轻量版
  - ③ LiteLLM 接入方式（与 paper-qa 同）
- **可借鉴程度：中**（企业级工程化参考，但太重）

### 10. FastGPT（labring）

- Star：约 **29k–30k**（vibecrowd 2026-07 报 28.9k；TMCnet 2026-08-19 报 29,387）【第三方数据】
- 架构形态：**可视化 RAG + Agent 工作流平台**（Next.js + TS + MongoDB + PG Vector/Milvus）
- 检索策略：**多路召回 + RRF 合并 + Rerank 二次排序**；支持 concat query（连续对话时拼历史 query 提升 rerank 准确率）【已核验 doc.fastgpt.cn】
- 引用：chunk-level 可编辑删除，答案带引用
- **对用户借鉴**：
  - ① **RRF + Rerank 的工程化实现**（用户已自己实现 RRF，可对照 FastGPT 的参数默认值）
  - ② **concat query**：多轮对话时把历史 query 拼进检索 query——用户做"多轮记忆"时可直接抄
  - ③ Web 前端架构（Next.js + ChakraUI）—— 用户做 Web 前端时可参考其交互
- **可借鉴程度：中**

## 四、开源类对个人项目的借鉴总结

### 4.1 用户当前技术栈 vs 开源标杆的差距

用户栈：DeepSeek API + Ollama bge-m3 + Chroma + 自实现 BM25 + RRF + 中英术语词典查询改写 + [n] 引用 + 多轮记忆。

对照上表，用户的栈**已经站在 paper-qa / OpenScholar 的肩膀上**：
- 混合检索（BM25 + dense + RRF）= RAGFlow / Onyx / FastGPT 的工业标配，**比 paper-qa（Numpy）和 chatchat（单路 dense）都先进**
- bge-m3 = 多语言 + dense/sparse/multi-vector，**比 QAnything 的 bce-embedding 和 paper-qa 的 OpenAI embd-3-small 更适合中文论文**
- DeepSeek API 通过 OpenAI 兼容协议接入 = paper-qa 用 LiteLLM 接入 DeepSeek 的同一条路

**真正缺的模块**（按优先级）：
1. **Rerank**（paper-qa 用 LLM rerank、OpenScholar/RAGFlow/QAnything 用 cross-encoder）—— 用户目前没有
2. **引用校验**（OpenScholar 的 posthoc attribution）—— 用户目前是"生成后映射"，缺一步 LLM 自检
3. **PDF 深度解析**（RAGFlow DeepDoc / paper-qa Docling）—— 双栏、表格、公式
4. **Agent 化检索**（paper-qa ToolSelector / OpenScholar self-feedback）—— 用户目前是单轮 RRF

### 4.2 直接可照搬的模块（按落地优先级）

| 优先级 | 模块 | 借鉴对象 | 落地建议 |
|---|---|---|---|
| **P0** | **引用 key 机制** | paper-qa | chunk 入库时分配 `pqac-<hash>` key；QA prompt 写死"用 (pqac-xxx) 引用"；生成后正则提取 → 映射回原文 → 渲染成 [1][2]。比"答案后处理数字映射"更稳。 |
| **P0** | **posthoc citation verification** | OpenScholar | 答案生成后，加一轮 LLM 调用："检查以上答案中每个需要引用的论断是否都挂了 [n]，缺了请补"。DeepSeek 完全能做，成本约 500 token。 |
| **P1** | **bge-reranker 接入** | OpenScholar / QAnything / RAGFlow | Ollama 跑 `bge-reranker-v2-m3`（与 bge-m3 同家族）或 HF 跑 `bge-reranker-large`，对 RRF 融合后的 top-20 做精排取 top-5。论文消融显示去掉 rerank 正确性掉 5-20 分。 |
| **P1** | **max_per_paper 去重** | OpenScholar | RRF 融合后，单篇论文最多留 3 个 chunk，避免一篇霸屏。一行 dict 操作。 |
| **P2** | **LLM-based contextual summary rerank** | paper-qa | 如果不想跑 reranker 模型，可以让 DeepSeek 对每个候选 chunk 写一句"结合 query 的摘要"再挑。适合 chunk 数 <20 的场景。 |
| **P2** | **concat query（多轮检索改写）** | FastGPT | 多轮对话时，把上一轮 query 拼进当前检索 query，提升多轮记忆下的召回。 |
| **P3** | **DeepDoc / Docling PDF 解析** | RAGFlow / paper-qa | 遇到双栏/表格/公式时，把 PyMuPDF 切换到 Docling 或 RAGFlow DeepDoc 后端。 |
| **P3** | **self-feedback loop** | OpenScholar | 面试亮点项：y0 → feedback → 补检索 → y1。M3 阶段再做。 |

### 4.3 需要改造的模块（OpenAI 依赖 → DeepSeek）

- paper-qa 用 LiteLLM → DeepSeek 是 LiteLLM 一等公民，`Settings(llm="deepseek/deepseek-chat")` 即可，**几乎零改造**
- OpenScholar 的 `--api openai --api_key_fp` 也是 OpenAI 兼容协议，DeepSeek 改 `base_url` 即可
- GPT-Academic / chatchat 手写 bridge → 不建议参考，直接用 LiteLLM 或 openai SDK 改 base_url

### 4.4 不值得借鉴的项目

- **GPT-Academic / ChatPaper**：不是 RAG，没有检索/引用/rerank 任何核心模块，star 高是因为功能广（翻译/润色/语音），不要因为 star 高就去读代码
- **KAG**：知识图谱构建成本对个人项目过高，论文问答场景收益不明显
- **chatchat**：2023 年的入门教程，架构比用户当前栈还基础

### 4.5 给用户下一步决策的建议

用户待决策：M3 写作助手 / Web 前端 / 会话管理 / Rerank 先做哪个？

**基于本次调研，建议优先级：**
1. **Rerank（bge-reranker）> 会话管理 > Web 前端 > M3 写作助手**
   - 理由：paper-qa 和 OpenScholar 的消融实验都表明 rerank 是正确性提升最大的单模块（去掉后掉 5-20 分），而用户目前没有；会话管理是多轮记忆的工程基础；Web 前端和 M3 写作助手是"锦上添花"。
2. 同时**强烈建议把 posthoc citation verification 加上**（P0，成本极低，只需一次额外 LLM 调用），这是 OpenScholar 论文证明有效的引用准确性提升手段，面试时讲"我做了引用自检"比"我做了引用映射"高一个档次。
